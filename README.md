# Haven Hostel Management

A local-first hostel management starter built with Node.js and SQLite. It uses Node's built-in HTTP, SQLite, and Argon2 modules, plus Nodemailer for SMTP OTP delivery. Node.js 24.7 or newer is required.

## Start locally

```powershell
npm run setup
npm run admin:create
npm start
```

Open `http://localhost:3000`. The health endpoint is `http://localhost:3000/api/health`. Setup generates a private local `.env` with an unpredictable authentication pepper and local Mailpit SMTP defaults, then migrates and seeds the database. It will not overwrite an existing `.env` or secrets. Start Mailpit before signing in; its default SMTP port is `1025` and inbox interface is `http://localhost:8025`. You can also set `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, optional `SMTP_USER`/`SMTP_PASSWORD`, and `MAIL_FROM` in `.env`. If SMTP is configured, OTPs are emailed and are not returned to the browser or printed in the server terminal. If SMTP is absent, `DEMO_OTP=true` in non-production enables the local demo-code fallback. In production, inject `AUTH_PEPPER` and SMTP credentials from a secret manager and leave `DEMO_OTP` disabled.

`npm run admin:create` securely prompts for the first Main Admin (Porter) account (password input is hidden). The four roles are Main Admin (Porter), Hall Master/Mistress, Hall President, and Student. Only Main Admin manages accounts, roles, and configuration backups; Hall Master/Mistress manages resident operations; Hall President is read-only; Students can submit and view only their own Haven Hall registration. Permissions are enforced by backend routes as well as the interface, and role changes are audited.

The account-creation form lets applicants select Student, Hall President, or Hall Master/Mistress. New accounts start with Student permissions; a Main Admin reviews any requested elevated role in **Admin → Active users** and assigns the approved role there. Main Admin is not available through public sign-up: create that account separately with `npm run admin:create`. Login continues to require the configured OTP step for every role.

If you forget an admin password, open a terminal in the project folder and run `npm run admin:reset-password`. Enter the admin's email and the new password twice when prompted; password input is hidden. This resets only an active admin account, stores a fresh salted Argon2id hash, revokes that admin's existing sessions and OTP challenges, and records an audit event. It does not delete users or hostel records.

To sign in as Main Admin, create the account with `npm run admin:create` in the project terminal. Enter the same email/password on the site, then retrieve the OTP from Mailpit at `http://localhost:8025` and enter it. Main Admin accounts open `/admin`; all other roles open `/dashboard`. The signed-in Main Admin navigation includes **Implementation report**, which displays project/security details and the current active account directory; account identifiers are only loaded from the Main Admin-protected API. In **Admin → Active users**, Main Admin can explicitly update non-admin accounts' roles, modify usernames, emails, or passwords, archive accounts for recovery, or permanently delete accounts. Permanent deletion removes only the account and its authentication sessions; hostel registrations and room records are preserved, and the deletion is audited. Main Admin accounts are protected from role changes, modification, archive, and permanent deletion; the table marks these rows as **Protected**. **Archived users** supports restore; restores reject active username/email conflicts. Archive and restore actions are audited and do not remove hostel records. Direct visits to `/reports`, `/admin`, `/dashboard`, and `/implementation-report` are supported, and unavailable pages redirect to the user's permitted home page.

The admin panel's **Backups** tab creates local AES-256-GCM encrypted snapshots of active user roles and system settings. Restoring applies only those settings and roles; it never includes or modifies hostel rooms or registrations. Keep `BACKUP_ENCRYPTION_KEY` backed up in a secret manager: encrypted backup files cannot be restored without it. Local snapshots are stored under `backups/` and excluded from source control.

The demo seed creates 15 rooms and 50 fictional hostel registrations. Re-running it leaves the seeded sample data unchanged. Student accounts submit their own Haven Hall registration from their dashboard; it remains pending until a Main Admin or Hall Master/Mistress chooses a room and checks the student in. Room capacity, availability, and gender compatibility are validated by the server. Staff can view room occupants, move residents, and check them out.

## Step-by-step development plan

1. **Database setup — started.** Create and migrate a relational schema for user identities, OTP challenges, room inventory, hostel registrations, system settings, and audit logs. Seed fictional demo records. Keep schema and business data in SQLite for local development.
2. **Authentication and identity — local demo implemented.** Validated registration creates a Student account and enforces unique, case-insensitive username/email identities. Passwords must be at least 8 characters (maximum 128 UTF-8 bytes) and are hashed using Node's Argon2id implementation with a per-user random salt stored separately and a pepper loaded from `.env`. Sign-in verifies the password, then issues a five-minute OTP challenge with attempt limits and replay prevention. Configured SMTP delivers OTPs by email; Mailpit is supported for local testing. If SMTP is not configured, `DEMO_OTP=true` outside production enables the development-only code display.
3. **Sessions and authorization — role controls implemented.** Backend routes enforce the four-role policy and audit changes. Main Admin can archive and restore accounts; restoration refuses active username/email collisions and the last Main Admin cannot be demoted or archived. SameSite cookies and same-origin mutation checks mitigate CSRF. Sessions are stored in SQLite as token hashes, expire after eight hours, survive server restarts, and are revoked on sign-out or user archival.
4. **Sensitive data and auditability.** Keep payment data out of scope unless a payment workflow is specifically approved. If required, use a payment provider token rather than storing card details. Encrypt any necessary sensitive fields with authenticated encryption and keys supplied by a secret manager. Record account, role, check-in/out, and configuration changes in append-only audit events, excluding secrets and credentials.
5. **Backup and restore — local configuration snapshots implemented.** Admins can create encrypted AES-256-GCM snapshots containing active user roles and system settings. Restore applies only those fields, audits the action, and leaves hostel rooms and registrations untouched; it rejects restores that would remove every active admin. AWS S3 upload, IAM integration, retention/lifecycle policy, and off-site restore testing remain to be configured.
6. **Operational UI and reports — demo implemented.** The responsive dashboard shows clickable resident, occupancy, pending, room-value, and room details; available beds; and registration, room assignment/move, check-in, and check-out controls. The Current residents detail includes a numbered room directory; each room shows its residents and contact details, permits staff to add a compatible pending student when a bed is available, and permits moving current residents to another compatible room. Main Admin and Hall Master/Mistress can manage residents; Hall President can view operations and reports; Students can submit and see only their own Haven Hall registration. Report summary cards open dedicated Check-ins, Check-outs, Pending, and Estimated Monthly Room Value pages. Check-in and monthly-value pages have numbered room selectors and room-specific resident details; report details provide navigation back to the hostel dashboard. The reports landing page also includes check-in activity and audit history. Server-side role checks, room capacity/gender checks, and audit events protect the operational API. Revenue is an estimated occupied-room value, not collected revenue. Online payment processing remains out of scope.
7. **Verification and delivery.** Add automated tests for migration/seed idempotence, unique identities, password and OTP flows, expiry and replay rejection, every role/action pair, archive recovery, and configuration-only restore invariants. Add security headers, dependency/security review, setup documentation, and an instructor-friendly demo walkthrough. Move from local SQLite to AWS RDS only when deployment requirements and concurrency needs justify it.

## Current scope and security notes

The current implementation includes a project page, SQLite migration and fictional seed data, local registration/sign-in with SMTP email OTP (Mailpit for local testing), persistent hashed sessions, admin role/archive/restore management, encrypted local configuration backups, and operational dashboard/check-in/report demos. Production email provider configuration, encrypted payment handling, AWS backup upload, online payments, and production deployment are not implemented. Do not deploy it as a production hostel system until those controls are implemented and tested.

The included HTTP server uses an explicit static-file allowlist and security headers. Do not add real student personal data to the demo database.
